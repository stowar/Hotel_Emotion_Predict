## 问题陈述

酒店行业每天产生海量中文用户评论，运营团队需要快速识别评论中的情感倾向（好评/差评），定位用户关注的关键词，以便及时响应客户反馈、监控口碑变化。人工逐条阅读评论效率低、主观性强，急需一套自动化的情感分析系统。

## 解决方案

端到端的中文酒店评论情感分析系统 — 基于 PyTorch（双向GRU + Self-Attention）深度学习模型，通过 FastAPI 提供 REST API 服务，前端使用 ECharts 实现注意力权重可视化。支持单条文本实时预测、批量 CSV/TSV 文件处理、注意力热力图展示，以及桌面 GUI 应用，开箱即用。

## 用户故事

1. 作为酒店运营人员，我希望输入一条评论文本即可获得情感预测结果和概率分数，以便快速判断客户满意度。
2. 作为数据分析师，我希望上传 CSV/TSV 评论文件进行批量预测并导出结果，以便高效分析海量评论。
3. 作为产品经理，我希望看到模型在做预测时重点关注了哪些词（注意力权重），以便理解决策依据。
4. 作为前端开发者，我希望 API 原生支持跨域，以便从任意域名直接调用接口。
5. 作为后端开发者，我希望一行命令即可启动 API 服务，以便快速集成到现有工作流。
6. 作为非技术用户，我希望有一个点击即用的桌面 GUI 和可视化图表，以便无需接触命令行或 API 工具。
7. 作为机器学习工程师，我希望在新数据上重新训练模型并调整超参数，以便针对特定酒店领域优化准确率。
8. 作为测试工程师，我希望在留出测试集上评估模型并获取准确率/损失指标，以便在部署前验证模型质量。
9. 作为运维人员，我希望系统能无缝兼容 GPU 和 CPU 环境，以便在不同硬件配置上运行。
10. 作为数据标注员，我希望批量预测界面支持点击切换标签来人工修正，以便在导出前修正低置信度预测。
11. 作为系统集成者，我希望 API 返回包含情感标签、概率、分词和注意力权重的结构化 JSON，以便下游系统使用。
12. 作为项目维护者，我希望数据处理、模型定义、训练、评估和推理模块职责清晰分离，以便独立维护。

## 实现决策

- **模型架构**: 双向GRU（2层，hidden_size=256）+ Self-Attention 注意力机制。GRU 相比 LSTM 训练更快、精度相当；Self-Attention 暴露每个词对预测的贡献，实现可解释性。
- **词嵌入**: 可训练的 Embedding 层（dim=128，padding_idx=0），从酒店评论语料从头训练，而非使用预训练词向量——系统自包含，无需外部模型下载。
- **API 框架**: FastAPI + Pydantic v2 做请求/响应校验。选择 FastAPI 而非 Flask 主要因为自动生成的 OpenAPI 文档（`/docs`）和原生异步支持。
- **跨域策略**: 完全开放（`allow_origins=["*"]`）——适合开发/内部工具场景，生产环境应限制来源。
- **中文文本处理**: jieba 分词（lcut 模式），推理阶段未启用停用词过滤（仅在 `constants.py` 中定义了停用词表供训练数据探索），错词修正词典已定义但主流程中未强制使用。
- **序列处理**: 固定最大长度 max_seq_len=50，超长截断（保留头部），不足补零。第 50 个词之后的内容被丢弃。
- **预测阈值**: 直接对 softmax 输出取 argmax（无阈值配置）。低置信度标记（<70%）仅在前端批量表格中做视觉提醒。
- **模型持久化**: `torch.save(model.state_dict(), ...)` 保存为 `.pt` 文件。API 启动时加载一次，常驻内存服务所有请求。
- **前端架构**: 单个静态 HTML 文件 + ECharts CDN。无构建工具、无框架。批量预测使用串行请求 + 80ms 间隔防止压垮后端。
- **历史存储**: 前端使用 localStorage（上限 20 条），后端的命令行预测工具和 GUI 将日志写入 `runs/logs/predict.txt`。
- **桌面 GUI**: 基于 Tkinter + matplotlib 嵌入式图表，与 Web API 独立入口。
- **训练配置**: Adam 优化器（lr=2e-4），CrossEntropyLoss，8 轮训练，batch_size=16。Windows 下 num_workers=0。
- **配置管理**: 集中在 `backend/config/settings.py` 的 CONFIG 字典中，无环境变量覆盖、无 CLI 参数配置。
- **项目结构**: 单一 Python 包（`backend/`），平铺式导入。训练/评估/预测脚本直接在 `backend/` 级别相互导入。

## 测试决策

- 好的测试验证外部行为：给定已知输入文本，模型返回正确的情感标签和合法的概率分布（两值均在 0-1 之间，和约等于 1）。
- API 端点测试：有效 JSON 的 POST `/predict` 返回 200 和正确响应结构；空文本返回友好错误；超长文本在 max_seq_len 约束内正常处理。
- 模型评估：留出测试集准确率为核心指标（当前 86.3%），训练损失收敛验证训练稳定性。
- 仓库中暂不存在单元测试。当前测试方式为手动执行 `evaluate.py` 和交互式使用 `predict.py`。
- 测试结构参考：`evaluate.py` 中的评估循环（model.eval() + torch.no_grad() + 准确率计算）可作为自动化集成测试的模板。

## 不在范围内

- 多分类情感（中性、混合）——当前仅支持二分类
- 细粒度情感分析（如"房间好但服务差"这类混合评价）
- 实时流式处理或 WebSocket
- 用户认证 / API Key / 频率限制
- 模型版本管理与 A/B 测试基础设施
- Docker 容器化
- CI/CD 流水线
- 云端部署（系统在本地 8000 端口运行）
- 多语言支持（仅中文）
- 预训练语言模型集成（BERT 等）

## 补充说明

- 模型在 1000 条测试集上达到 86.3% 准确率，avg_loss=0.028——对于从零训练的 GRU+Attention 模型来说是不错的基线。
- 数据格式为 TSV，两列：评论文本（tab）标签（0=负面，1=正面）。`train.tsv` 和 `test.tsv` 均在仓库中。
- 前端有一个巧妙的半自动标注功能：点击批量结果中的标签数字可在正负面之间切换，导出前支持人工修正。
- 注意力热力图可视化是本项目的核心亮点——让"黑盒"模型的决策过程对非技术用户透明可见。
- 代码中存在一处拼写：`tarin.py`（应为 `train.py`）——可能是有意保留或历史遗留，重构时值得注意。
- `runs/` 目录包含训练好的模型权重和训练日志——已提交到仓库（12MB+），对小型项目可接受，规模增大后建议使用 git-lfs。
